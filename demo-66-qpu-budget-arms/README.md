# Demo 66: Accepted Hardware Results per QPU-Second: Default, Rule-Based and Agent-Planned Hybrid Quantum Workflows under a Fixed Budget

> **▶️ New here? Follow the step-by-step [Execution Instructions](INSTRUCTIONS.md)** — every command with expected output.

**Status (19 November 2026):** design stage. A teaching toy with labelled synthetic fixtures runs offline and its tests pass. **No pilot data have been collected and no results exist.** Every study quantity is `[RESULT PENDING]`.

## Research question

Under a fixed, small budget of quantum-processor (QPU) time, does a workflow in which an AI agent simulates each job classically with a device-derived noise model before deciding whether, and how, to submit it return more results within a registered tolerance of the classical reference per QPU-second than the provider's default pipeline and a rule-based, calibration-aware pipeline with standard error mitigation?

## Why it matters

Free and allocated cloud quantum access is measured in minutes, and a job that fails, is too deep for the device or returns an estimate swamped by noise spends that time without producing a usable result. The pilot asks whether a simulate-first decision step changes the yield, and it is designed so that 'no better than the rule-based baseline' is a reportable outcome.

## Design of the pilot study

| Arm or control | What it is |
|---|---|
| B0 | provider default: default compilation, no mitigation, every job submitted |
| B1 | rule-based and calibration-aware: skips jobs predicted not to fit or to be swamped by noise, applies zero-noise extrapolation |
| A2 | a fixed open-weight model run locally that plans, simulates, mitigates and schedules (the teaching toy replaces it with a deterministic stand-in) |

**Outcomes**
- primary: accepted results per simulated QPU-second (an estimate is accepted when it lies within the registered tolerance of the classical reference)
- secondary: QPU-seconds lost to failed or rejected jobs; shots and time to the first accepted result; model tokens per accepted result

**How the pilot runs.** Six to ten instances from two workload families, noisy simulation with a fake backend from qiskit-ibm-runtime's fake_provider (calibration snapshots of real devices), zero-noise extrapolation with Mitiq, and a simulated QPU-time budget. Arms B0, B1 and A2 only; a frontier-model arm is not run in the pilot. No real quantum hardware is used. Any figure from the pilot is a simulation-based feasibility check on N instances, never hardware evidence. The steps are in [`ZCODE_PROMPT.md`](ZCODE_PROMPT.md); the study is registered in `docs/` before the first real run.

**Data.** Synthetic instances in the toy; in the pilot, circuits generated by committed scripts and classical reference values computed exactly on small instances.

## The teaching toy

`student/qpu_budget.py` implements the measurement on `fixtures/battery.json`; `student/run_qpu_budget.py` prints one line per case and writes `results/qpu_budget.json`. Every number it prints belongs to the toy fixture and is not evidence about any real system, dataset or population.
